# ADR-0001 模块化单体

- 状态：已接受（AI 建议，用户默认）
- 日期：2026-11-15
- 相关需求：REQ-001–REQ-034，尤其 REQ-028–REQ-031

## 背景

LingoCurrent 是新项目，一人维护，目标为一年内 1,000 账号、100 人同时使用。网站与应用计算限定 Vercel，数据库 Neon、身份 Clerk 已由产品阶段确定。没有已存在的系统需要迁移。

## 候选方案

| 方案 | 优点 | 缺点 | 适合条件 |
|---|---|---|---|
| 模块化单体 | 单一发布单元、同库事务，运维工作较少 | 必须约束内部依赖，后台工作需按函数资源分段 | 当前维护人力与容量目标 |
| 微服务 | 可独立发布、隔离和扩容 | 网络失败、跨服务一致性、部署排查均更复杂 | 模块已出现明确独立扩容或团队所有权需求 |
| 无边界单体 | 初期编写简单 | 阅读/音频/AI/词卡/进度易耦合，修改难验证 | 很小且短期的一次性工具，不符合本项目完整流程 |

## 决策

采用模块化单体：一个应用代码库和发布单元，内部划分业务所有权。Vercel 可将 HTTP 与后台入口运行在不同无状态函数实例，但它们不形成独立微服务，也不各自拥有一套数据库。

用户在架构访谈第二轮回答“you suggest”，采用推荐项；技术边界将在 overview 与后续 ADR 中具体定义。将同步请求与可恢复后台工作区分，是为满足函数生命周期及发布一致性要求，不是新增独立服务器。

## 证据

已阅读全部产品规格；无应用代码、性能测试或部署结果。指标来自 `docs/architecture/inputs.md`，不能把架构选择当作 100 人并发已达标。

## 后果

- 好处：核心写操作可以使用同一数据库事务；配置、发布和日常排查集中。
- 代价：需要架构检查约束模块边界，函数之间仍需使用数据库共享任务与进度，不依赖进程内状态。
- 重新考虑条件：staging 或生产观测证明某模块无法在既定 Vercel 形态满足容量，或出现真实独立发布需求；改变计算平台前仍需用户决定。
